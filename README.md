# LeadDesk Mini

A small, production-shaped lead capture app: a public landing page whose form
writes straight into Postgres, and a password-protected admin inbox where those
leads are searched, qualified by budget and moved from **New → Contacted →
Closed**. Validation is defined once in Zod and enforced on both the browser and
the server, and the admin area sits behind real credential authentication with
bcrypt-hashed passwords — there is no hardcoded password anywhere in the
codebase.

---

## Tech Stack

| Choice | Why |
| --- | --- |
| **Next.js 16 (App Router, TypeScript)** | One deployable unit for the marketing page, the admin UI and the API. Server Components keep the session check on the server, where it can't be bypassed. |
| **PostgreSQL on Supabase** | A real relational database with proper enum types and indexes, on a free tier that doesn't sleep. |
| **Prisma** | Typed queries generated from the schema, plus a migration history that can be replayed onto a fresh database with one command. |
| **Zod** | The validation schema is a value, so the *same object* runs in the browser and in the route handler. No second copy to drift. |
| **react-hook-form + @hookform/resolvers** | Uncontrolled inputs mean typing doesn't re-render the form, and the zod resolver wires the shared schema straight into field-level errors. |
| **Auth.js (NextAuth v5), Credentials provider** | Session cookies, CSRF and JWT signing handled by a maintained library rather than hand-rolled. Credentials-only keeps the surface small — no OAuth apps to register. |
| **bcryptjs** | Deliberate over the native `bcrypt`: pure JavaScript, so there's no native module to compile on Vercel's build image. Same algorithm and cost factor. |
| **Tailwind CSS v4** | Styling stays next to the markup; no separate stylesheet to keep in sync with the component tree. |
| **Vercel** | First-party Next.js hosting; `git push` deploys. |

## Data Model

Two tables, defined in [`prisma/schema.prisma`](prisma/schema.prisma).

### `Lead` (`leads`)

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Primary key, generated by the database. |
| `name` | `text` | 2–80 characters, trimmed before saving. |
| `email` | `text` | Lowercased and trimmed. Deliberately **not** unique — the same person may legitimately enquire twice. |
| `budgetRange` | `BudgetRange` enum | `UNDER_1K`, `FROM_1K_TO_5K`, `FROM_5K_TO_20K`, `OVER_20K`. |
| `message` | `text` | 10–2000 characters. |
| `status` | `LeadStatus` enum | `NEW` \| `CONTACTED` \| `CLOSED`, defaults to `NEW`. |
| `createdAt` | `timestamp` | Defaults to `now()`. |
| `updatedAt` | `timestamp` | Maintained by Prisma's `@updatedAt`. |

### `AdminUser` (`admin_users`)

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Primary key. |
| `email` | `text` | **Unique** — it's the login identifier, so duplicates must be impossible at the database level, not just in application code. |
| `passwordHash` | `text` | A bcrypt digest. Plaintext is never written to this column. |
| `createdAt` | `timestamp` | Defaults to `now()`. |

### Why status is an enum

`status` drives the entire workflow, so the set of legal values is a
correctness concern, not a formatting one. As a Postgres `ENUM`:

- the **database** rejects a bad value even if a bug or a manual `psql` session
  tries to write one — the constraint doesn't depend on application code being
  right;
- Prisma generates a **closed TypeScript union**, so a typo like `"CONTACTED "`
  fails at compile time rather than silently creating an orphan bucket;
- reporting stays honest. With a free-text column, `"closed"`, `"Closed"` and
  `"CLOSED"` are three different states and every count is wrong.

The same reasoning applies to `budgetRange`: these are analytics buckets, and
buckets that can be spelled two ways are not buckets.

### Why the timestamps exist

`createdAt` is the inbox's sort key — "newest first" is the default view, and
"how long has this person been waiting?" is the first question anyone asks about
a lead. `updatedAt` records when the status last moved, which is what
distinguishes a lead contacted this morning from one that has been sitting in
`CONTACTED` for three weeks.

### Search and indexing

Search is a server-side Prisma query
([`src/lib/leads.ts`](src/lib/leads.ts)) — the browser never receives rows it
isn't allowed to see and then filters them:

```ts
where.OR = [
  { name:  { contains: search, mode: "insensitive" } },
  { email: { contains: search, mode: "insensitive" } },
];
```

Three indexes are declared:

- **`status`** — the status filter and any per-status count hit this directly.
- **`email`** — supports exact lookups and prefix matching.
- **`createdAt`** — the default `ORDER BY createdAt DESC`. Without it, Postgres
  sorts the whole table on every single page load.

One honest caveat: `mode: "insensitive"` compiles to `ILIKE '%term%'`, and a
leading wildcard means a btree index **cannot** be used — that search is a
sequential scan. At the scale this app is built for (thousands of leads) that is
comfortably fast and the right trade for simple, obvious code. The next step, if
the table grew past a few hundred thousand rows, would be a `pg_trgm` GIN index.

Pagination is offset-based (`skip`/`take`, 25 per page) with a
`[createdAt DESC, id DESC]` sort — the `id` tiebreaker stops rows from
reshuffling between pages when two leads share a timestamp.

## Auth Approach

The goal is that **the application never knows any admin password**, so there is
nothing to leak from the source, the environment, or the database.

### 1. The password is hashed before it is ever stored

[`prisma/seed.ts`](prisma/seed.ts) reads `SEED_ADMIN_EMAIL` and
`SEED_ADMIN_PASSWORD` from the environment and runs the password through bcrypt
at **cost factor 12** before writing it:

```ts
const passwordHash = await hash(password, 12);
await prisma.adminUser.upsert({
  where: { email },
  update: { passwordHash },
  create: { email, passwordHash },
});
```

bcrypt is deliberately slow (~250 ms per hash) and salts every digest
individually, so two admins with the same password get different hashes and a
stolen database can't be attacked with a precomputed rainbow table. The
plaintext exists only in the environment variable used to run the seed.

### 2. Login verifies by re-hashing, never by comparing secrets

When someone submits the login form, the credentials go to a **server action**
([`src/app/admin/actions.ts`](src/app/admin/actions.ts)) — so the password
travels in a POST body and never lands in client-side JavaScript state — which
calls Auth.js `signIn()`. The Credentials provider's `authorize()` callback
([`src/auth.ts`](src/auth.ts)) then:

1. re-validates the payload with the shared `loginSchema`;
2. looks up the `AdminUser` by email;
3. calls `bcrypt.compare(submittedPassword, storedHash)`, which re-hashes the
   attempt using the salt embedded in the stored digest and compares the
   results;
4. returns the user's `{ id, email }` on a match, or `null` on any failure.

Two details worth calling out. A failed lookup still performs a dummy
`compare()` so that "no such account" and "wrong password" take the same amount
of time — otherwise response latency becomes a free account-enumeration oracle.
And both failure modes return the same generic message, for the same reason.

### 3. A signed JWT session cookie is issued

On success Auth.js issues a **JWT session cookie**, configured in
[`src/auth.config.ts`](src/auth.config.ts):

- `strategy: "jwt"` — required for Credentials logins, which don't go through a
  database adapter;
- signed and encrypted with `NEXTAUTH_SECRET`, so its contents can't be read or
  forged client-side;
- `httpOnly` — unreadable from JavaScript, which takes session theft off the
  table for an XSS bug;
- `secure` and `__Secure-`-prefixed automatically in production, so it is never
  transmitted over plain HTTP;
- `sameSite: lax`, which blocks the cookie from riding along on cross-site
  requests;
- `maxAge: 7 days`.

The `jwt` callback copies the AdminUser's database id onto the token on first
sign-in; the `session` callback mirrors it onto `session.user.id`.

### 4. Protected routes check the session — in two independent places

**Layer one — [`src/proxy.ts`](src/proxy.ts)** (Next.js 16 renamed the
`middleware` file convention to `proxy`). It runs before any matched route and:

- lets `POST /api/leads` through anonymously — that's the public form;
- returns **401 JSON** for every other `/api/leads` request without a session
  (an API client gets a machine-readable error, not an HTML login page);
- redirects anonymous visits to `/admin/*` to `/admin/login?callbackUrl=…`;
- bounces already-signed-in users away from the login page.

**Layer two — the handlers themselves.** Every protected route calls
`requireSession()` ([`src/lib/api-auth.ts`](src/lib/api-auth.ts)) and `/admin`
re-checks `auth()` server-side. This is not redundant paranoia: proxy protection
hinges on a single `matcher` array, and one typo there would silently make a
route public. The second check means each route is safe on its own terms.

### Why this beats a hardcoded password check

A hardcoded comparison — `if (password === process.env.ADMIN_PASSWORD)` — fails
on several counts:

- **The secret exists in plaintext** in source or in an env var, so it's exposed
  by any config leak, log dump, or screenshot, and it's visible to everyone with
  repository or dashboard access.
- **`===` on strings is not constant-time**, leaking information through timing.
- **It doesn't scale past one user.** There is no per-user identity, so you
  cannot add a second admin, revoke one, or attribute an action.
- **Rotation means a redeploy**, so in practice it never gets rotated.
- **There's no session.** Either the password is re-sent on every request, or
  you hand-roll a token — which is precisely the part that's easy to get wrong.

With bcrypt + Auth.js, the database holds only irreversible digests, admins are
real rows that can be added or removed without a deploy, sessions are signed and
expire on their own, and cookie handling is a maintained library's problem
rather than ours.

## Local Setup

**Prerequisites:** Node.js 20.9+ and npm. A Supabase project (free tier) or any
Postgres 14+ instance.

**1. Clone and install**

```bash
git clone <your-repo-url> && cd leaddesk-mini && npm install
```

`npm install` runs `prisma generate` via the `postinstall` script, so the typed
client is ready immediately.

> **Note on npm 11:** this project pins install-script approvals in
> `package.json` under `allowScripts` — Prisma needs its `postinstall` to fetch
> the query engine. If npm reports blocked install scripts, run
> `npm approve-scripts --allow-scripts-pending`.

**2. Configure the environment**

```bash
cp .env.example .env
```

Fill in `.env`:

- `DATABASE_URL` — Supabase → **Project Settings → Database → Connection string
  → Transaction pooler** (port `6543`). Keep the
  `?pgbouncer=true&connection_limit=1` suffix.
- `DIRECT_URL` — the same credentials on the **session** connection (port
  `5432`). Migrations need this; see [Deployment](#deployment).
- `NEXTAUTH_SECRET` — generate one with `openssl rand -base64 32`.
- `NEXTAUTH_URL` — `http://localhost:3000` locally. This must match the origin
  you actually browse to, or post-login redirects go to the wrong host.
- `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` — the first admin account. The
  seed refuses passwords under 10 characters.

**3. Create the schema**

```bash
npx prisma migrate deploy
```

**4. Seed the database**

```bash
npx prisma db seed
```

This creates the admin user and, **only if the `leads` table is empty**, eight
realistic demo leads with mixed statuses and backdated timestamps. Re-running it
rotates the admin password rather than failing, which makes it a usable "reset
my admin account" command; it will never overwrite real leads.

**5. Run it**

```bash
npm run dev
```

Landing page at `http://localhost:3000`, admin at `/admin`.

## Deployment

### Supabase

1. Create a project and save the database password.
2. **Project Settings → Database → Connection string**, and copy **both**:
   - the **Transaction pooler** string (port `6543`) → `DATABASE_URL`
   - the **Session / direct** string (port `5432`) → `DIRECT_URL`
3. Apply the schema from your machine: `npx prisma migrate deploy`
4. Seed the admin account: `npx prisma db seed`

**Why two URLs.** Vercel runs each request in a short-lived serverless function,
and each one opens its own database connection. Pointed at Postgres directly, a
modest traffic spike exhausts the connection limit and every subsequent request
fails. The transaction pooler (pgbouncer) multiplexes many function invocations
onto a few real connections, which is why `DATABASE_URL` uses it. But pgbouncer
in transaction mode can't hold the session state that `CREATE TYPE` /
`ALTER TABLE` need, so migrations use `DIRECT_URL` instead.
`?pgbouncer=true&connection_limit=1` tells Prisma to stop emitting prepared
statements, which pgbouncer cannot cache.

### Vercel

1. Push to GitHub.
2. Vercel → **Add New → Project** → import the repo. The framework preset is
   detected automatically; no build settings need changing.
3. Add these environment variables (Production **and** Preview):

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | Supabase pooled string, port 6543 |
   | `DIRECT_URL` | Supabase direct string, port 5432 |
   | `NEXTAUTH_SECRET` | `openssl rand -base64 32` |
   | `NEXTAUTH_URL` | `https://<your-app>.vercel.app` |

   `SEED_ADMIN_*` are **not** needed on Vercel — seeding runs from your machine.

4. Deploy.

`postinstall` runs `prisma generate` on every build, which Vercel requires: its
build cache would otherwise reuse a stale generated client and fail with type
errors after a schema change. `prisma/migrations/` is committed, so a fresh
database can be brought fully up to date with `npx prisma migrate deploy`.

## Test Credentials

Whatever you set in `.env` before running `npx prisma db seed`. The values in
`.env.example` are placeholders, not working credentials.

| Field | Value |
| --- | --- |
| URL | `/admin/login` |
| Email | value of `SEED_ADMIN_EMAIL` (suggested: `admin@leaddesk.test`) |
| Password | value of `SEED_ADMIN_PASSWORD` at seed time |

Re-running `npx prisma db seed` resets the password to the current value of
`SEED_ADMIN_PASSWORD`, so a forgotten password is a one-command fix.

## Known Limitations

Things deliberately left out, and what they'd cost to add:

- **No rate limiting.** `POST /api/leads` is public and unthrottled, so it can
  be flooded. A real deployment wants an IP-based limit (Vercel KV / Upstash)
  and probably a CAPTCHA or honeypot field.
- **No email notifications.** A submitted lead lands in the database and nowhere
  else — nobody is told about it. Nor is the submitter's address verified, so
  the email on a lead is unconfirmed.
- **No admin self-service.** Accounts are created only by the seed script. There
  is no signup, no password reset, no "change my password" screen, and no roles
  — every admin can do everything.
- **Pagination is offset-based.** `skip`/`take` is simple and correct here, but
  deep pages get slower, and a lead created mid-session can shift the window
  (the client de-duplicates by id to keep a row from appearing twice). Cursor
  pagination would be the fix.
- **Search can't use an index.** As explained above, `ILIKE '%term%'` forces a
  sequential scan. Fine at this scale; wants `pg_trgm` at a much larger one.
- **No soft delete or audit trail.** Status changes overwrite the previous value
  with no record of who changed what, and leads can't be deleted at all.
- **No automated tests.** The build is type-checked and the flows were verified
  by hand; there is no test suite guarding against regressions.
- **Single light theme.** No dark mode, and the admin table scrolls horizontally
  on a phone rather than reflowing into cards.
- **Sessions can't be revoked early.** JWT sessions are stateless, so a stolen
  cookie stays valid until it expires (7 days). Revocation would need a database
  session strategy or a token denylist.
- **`NEXTAUTH_URL` must be exact.** Auth.js rewrites the request origin to this
  value, so a wrong or missing entry sends post-login redirects to the wrong
  host. Vercel preview deployments get generated URLs and need their own value.
- **Pinned to Prisma 6.** Prisma 7 moves seed configuration out of
  `package.json` into a `prisma.config.ts` file and changes the generated client
  import path. `npx prisma db seed` prints a deprecation warning about
  `package.json#prisma` today; upgrading later means moving that one key into a
  config file.
- **Auth.js v5 is still a beta release.** It is what NextAuth ships for the App
  Router and is widely used in production, but the API can still shift between
  beta versions, so the dependency is worth pinning before a long-lived deploy.
